# 准确率与延迟的架构权衡

> 学习序号 06 · 清单 #6 · Domain 3: Integration（19%）。核查日期：2026-09-12。
> 考试依据：[Exam_Guide.md](../../../Exam_Guide.md) 第 6 节原文 “Evaluate accuracy-latency trade-offs and justify configuration decisions”；第 8 节样题侧重在场景约束下选唯一最佳方案，并解释错项。这里不把某个具体模型的实时速度或价格当作考点。

## 1. 目标不是“越快越好”

架构选择是一个**受约束优化问题**：在明确的准确率、安全下限以及 p95 端到端延迟上限内，选择维护成本可接受的配置。不能把准确率和延迟当作单一固定的反比关系：删除无关工具、修复错误的检索索引或复用稳定的 prompt 前缀，可能同时改善质量与响应速度；增加验证调用则可能增加两者中的质量与耗时。是否有效要实测。

先定义业务任务的“准确”：客服查询可以是答案有正确依据且无越权；退款决策还需要金额、订单归属、策略判定都正确。选择指标要按任务：分类可测 macro-F1；问答可测基于证据的正确率、拒答/引用准确性；工具执行可测任务完成率及错误副作用。对高风险任务，平均分不能掩盖少数严重错误。延迟同时测 **TTFT**（首个可见 token 时间）、完整响应时间、工具往返、p50/p95/p99 和超时率；异步任务可以另设完成时限。流式输出改善用户感知的首字响应，却不一定减少完整结果交付时间。[Streaming messages](https://platform.claude.com/docs/en/build-with-claude/streaming)

## 2. 用 critical path 分解延迟

```text
入口/鉴权 → 查询与检索 → Claude 调用 → 工具往返/下游 → 验证 → 输出
```

端到端完成时间 ≈ 串行阶段之和 + 并行阶段的最慢分支 + 排队与重试。两个独立只读查询若串行需 400 ms + 500 ms，则理想并行下临界路径趋近 500 ms，**不是保证刚好 500 ms**，还需计入调度、限流及合并；如果 B 依赖 A，则不可为“降延迟”并行。并行请求越多也可能挤占资源、增加下游 p95。[Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)

不同延迟根因需要不同修复：TTFT 长先查输入处理、队列及 cache 命中；工具阶段慢先查下游调用与串并行关系；生成阶段慢查输出长度及额外模型回合。不要仅因 p95 高就盲换模型。

## 3. 典型配置及其权衡

| 决策 | 可能的质量收益 | 延迟代价或收益 | 何时合理 / 警惕 |
|---|---|---|---|
| 单次 Claude + 必要上下文 | 减少编排环节、可能已足够准确 | 通常少一次或数次往返 | 基线方案；复杂任务可能不足 |
| Prompt chaining / 校验关卡 | 拆解任务、捕获部分错误 | 增加串行模型调用 | 有明确可检查子步骤且实测改善质量 |
| Agent 多轮工具探索 | 可处理不可预知步骤与环境反馈 | 工具和模型回合增多，尾延迟可能增长 | 开放式任务；固定分类不必用 |
| 路由到不同处理路径 | 难题用更强路径，简单题走快路径 | 路由本身耗时并有误判 | 用完整混合流量验证；不能让误路由破坏安全底线 |
| 独立工具并行 | 质量可保持，数据更及时 | 缩短临界路径；或增加竞争 | 只并行独立、无冲突的操作 |
| 更多检索/验证 | 可能提高证据覆盖与可靠性 | 检索、rerank、再生成都增加时间 | 针对检索或证据问题；不是越多越准 |
| Prompt caching | 同样的静态前缀不必重复处理 | cache 命中时通常降低 TTFT；miss 仍有开销 | 前缀稳定且重复频繁；需要核查命中率 |
| Streaming | 不自动提高准确率 | 改善感知等待，不必然缩短总耗时 | 适合用户能逐步阅读的文本；需要完整验证的结果不能提前当成功 |

Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 指出 agentic 方案常以延迟和成本换取任务表现；prompt chaining 用更多串行步骤换可检查性；简单调用或 augmented LLM 往往应作为对照。该文章发布于 2024-12-19，文章本身注明工具景观已变化；这里只使用其稳定的架构推理，不沿用旧模型/SDK 举例。

Anthropic 的 [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) 文档确认可重复前缀在 cache 命中时改善长输入的 TTFT；它不会凭空改进错误证据或业务逻辑。具体 TTL、计费、最短前缀、cache invalidation 为会变化的实现细节，不是 Guide 要求死记的数字。

## 4. 决策流程：先测，再做 Pareto 比较

1. 定义任务层级和硬约束。例如普通工单查询：基于证据的正确率 ≥ 设定阈值、p95 完整响应 ≤ SLA；高风险动作：授权检查与审批**不可被性能优化绕过**。
2. 构造代表真实流量的样本：简单/困难、长短输入、检索命中/未命中、工具错误、不同租户、冷/热 cache。留出独立集防止过拟合。
3. 建立简单基线；记录质量指标、TTFT、p95 总时长、各阶段耗时、超时率、成本和副作用。对比配置必须使用相同数据与负载条件。
4. 找瓶颈及错误类型，再增加**有因果假设**的干预：错误源于旧文档先修索引；工具串行且互不依赖再并行；复杂推理失败才考虑更复杂 workflow。
5. 对照取 Pareto 可行解：若 A 的质量不低于 B，p95 不高于 B 且至少一项更优，B 被支配；若质量改善但 p95 超 SLA，则不选，或设计清晰的异步/分流路径。
6. 生产中持续测不同流量段的质量与尾延迟；路由、缓存和模型快照改变后重测。不要只报告平均值。

例如下面是**教学用虚构测量**，不是 Claude 性能宣称：

| 配置 | 离线正确率 | 线上 p95 完整时长 | 判定（若目标 ≥90%、≤3 秒） |
|---|---:|---:|---|
| A：单次调用 | 91% | 2.2 秒 | 满足 |
| B：每次串行二次验证 | 94% | 4.1 秒 | 违反时限 |
| C：简单请求 A；复杂请求人工/异步验证 | 需按真实路由混合流量测 | 需测 p95 与完成率 | 尚无充分数据，不能宣布获胜 |

不要仅凭表中 C 的设想得出“路由一定最优”；需要测误路由的错判及用户是否接受异步结果。业务可定义“快速初步答复 + 最终验证”两个 SLA，但不得把未验证初稿伪称最终正确答案。

## 5. 四个容易混淆的点

- **TTFT vs total latency**：streaming 能更早显示文字，若用户必须等完整 JSON 或审批后执行，则成功时刻应按完成/验证计。
- **并行 vs 重复验证**：独立读取可并行；依赖前一步结果的验证必须后置。多次投票也非免费的确定性真理。
- **更多上下文 vs 更高准确率**：增加无关检索片段可能干扰模型，还会增加输入处理；先审检索质量和上下文相关性。
- **低延迟 vs 权限绕过**：权限校验、租户隔离、必要的 human approval 是硬约束，不能为了 SLA 移走；应调整任务路径或重新谈 SLA。

## 6. 实际 Claude 场景与 failure modes

客服 agent 查询订单状态，要同时查订单记录和配送事件。若两者都只需要可信订单 ID，可在编排层并行读，校验租户权限后合并证据交给 Claude；若配送查询依赖先由订单查询获得的 tracking ID，则必须串行。对常见请求可以使用单轮回答；只有遇到证据冲突或任务不确定时启动额外验证，并测量混合流量的质量与尾延迟。

常见失败包括：只测模型生成时间，遗漏检索/工具和队列；在 cache 热态测压却忽略首次请求；为所有简单问题加 evaluator 循环导致 p95 失控；流式输出未完成时就报告业务成功；平行工具在有依赖或写冲突时造成旧数据/重复副作用；路由错误让高风险任务进入弱校验路径。并行工具实际结果需正确关联并全部处理，不能只等最快一个。
